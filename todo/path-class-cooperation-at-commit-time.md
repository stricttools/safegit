# Cooperate with the repository's path-class declarations at commit time

## Context

Repositories in this fleet are moving to a per-repository declaration of
what every tracked path is, kept in a directory under `.stricttools/` that
the release tooling owns. Each pattern in it carries two facts: the origin
of the path, authored by a person or agent versus generated by a tool, and
its mutability, editable, read-only, or append-only. Generated paths also
name the tool that writes them and the command group that regenerates and
checks them. Generated files carry a stamp on their first lines saying so.
Release-time checks enforce the declarations against the tree and against
the previous release tag, and that enforcement is the authority.

safegit is the only commit door in these repositories, and the only tool
that sees a change at the moment it is made. Everything below is a chance
to refuse a wrong change immediately rather than at the next release. None
of it is required for the declarations to work; all of it makes the fleet
nicer to live in, and each item is independent.

## Problem

Today a person or agent can commit a hand edit to a generated file, an edit
to a locked release archive, a rewrite of an append-only log, or a file
under an ignored scratch directory, and nothing says a word until a release
is attempted, often by someone else, days later.

## Opportunities

1. **Refuse a commit that hand-edits a generated path.** If a path the
   declarations mark as generated is in the commit and the commit does not
   arrive through the generator's own commit path (recognizable by the
   trailer that marks machine-made commits), refuse with the remedy naming
   the generator's command group and the source file to edit instead. The
   source file is in the file's own stamp.
2. **Refuse a commit that touches a read-only path.** Locked release
   archives, release records, and todo files are declared read-only; any
   change, deletion, or rename in a commit is refused unless the commit
   arrives through the tool that owns the path.
3. **Refuse a non-append change to an append-only path.** For a path
   declared append-only, the committed blob must begin with the previous
   blob's content; anything else is refused with a sentence saying which
   line was the first to differ and that the file grows only at its end.
4. **Refuse a commit that adds a file under an ignored directory.** A path
   that `.gitignore` matches but is being added anyway (a forced add, or a
   missing ignore file) is refused, since scratch and rendered-at-use
   directories are never committed.
5. **Verify the stamp on generated files.** When a generated path is
   written through the sanctioned path, check that its first lines carry the
   fleet stamp, so an old generator that predates the stamp is caught at the
   first commit rather than at release.
6. **Write a trailer naming the writer.** When committing on behalf of a
   generator, add a trailer naming the tool, its version, and the command
   group, so the history says who wrote each generated change and the
   release-time check can cross-check trailers against declarations.
7. **Apply file modes from the declarations on clone and checkout.** Git
   stores only the executable bit, so the read-only modes the release
   tooling sets vanish in every fresh clone. A clone or checkout through
   safegit can re-apply read-only mode to every path declared read-only or
   append-only, restoring the local courtesy that makes an accidental edit
   fail at the editor.
8. **Keep path history for generated files across moves.** safegit already
   records moves in trailers; extending that to note when a moved path was
   generated lets a later reader know the file's origin did not change with
   its name.
9. **Read the declarations through one shared matcher.** The declarations
   use git's ignore-pattern syntax so that every reader agrees; safegit
   needs a matcher in Go that treats patterns the way git does, and it is
   worth sharing with any other Go reader in the family rather than writing
   a second one.

## Solutions

### A. Implement the refusals as commit-time checks inside safegit (recommended)

Each opportunity becomes a check run inside `safegit commit` before the
commit is authored, reading the declarations directory and the stamp, with
its own refusal sentence and remedy, and a red-green test per refusal.

- Pro: the earliest possible refusal, in the tool that already owns commits.
- Pro: independent items, adoptable one at a time.
- Con: a second implementation of the pattern matcher and the class rules
  beside the release tooling's; the two must be tested against the same
  cases.

### B. Delegate to the release tooling's check from the commit hook

Have `safegit commit` invoke the release tooling's path-class check on the
staged tree and refuse on its verdict.

- Pro: one implementation of the rules.
- Con: a process spawn per commit, a dependency on the other tool being
  installed, and no access to the commit's own trailer-to-be.

### C. Do nothing; rely on release-time enforcement

- Pro: nothing to build.
- Con: every wrong commit is found late, by someone else.

## Affected files

- The commit command and its pre-authoring checks.
- The trailer package, for the writer trailer and the move note.
- A new declarations reader and pattern matcher.
- The clone and checkout paths, for mode application.
- The test suite, one red-green test per refusal and per remedy.

## Effort

Items 1 to 4: a few days together, since they share the reader and the
matcher. Items 5 and 6: a day. Item 7: a day, plus the decision of which
commands apply modes. Items 8 and 9: a day each.
